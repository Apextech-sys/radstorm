# Glossary

Definitions of terms used throughout the radstorm documentation. This document is for network engineers who know RADIUS but may not know the specific abbreviations and conventions used in this tool.

---

**Acct-Session-Id**
RADIUS attribute 44. A unique string identifying an accounting session, generated by the NAS for each subscriber session. radstorm generates a unique Acct-Session-Id per subscriber per run. The RADIUS server uses this to correlate Accounting-Start, Accounting-Interim-Update, and Accounting-Stop records.

**Acct-Status-Type**
RADIUS attribute 40. Distinguishes between Accounting-Request subtypes: `1` = Start (session opened), `2` = Stop (session closed), `3` = Interim-Update. radstorm sends only Start records (`include_acct_start = true`) — it does not simulate session lifetimes.

**Authenticator (Request)**
A 16-byte field in the RADIUS packet header. For Access-Request: randomly generated by the NAS (radstorm). Used to encrypt the User-Password in PAP and to validate the Response Authenticator. For Accounting-Request: MD5(Code | Identifier | Length | 16-zero-bytes | Attributes | SharedSecret).

**Authenticator (Response)**
The 16-byte field in reply packets (Access-Accept, Access-Reject, Accounting-Response). Computed as MD5(Code | Identifier | Length | RequestAuthenticator | Attributes | SharedSecret). radstorm validates this on every reply. A mismatch means the server used a different shared secret — the reply is dropped and logged.

**Authenticator (Message)**
See Message-Authenticator.

**AVP (Attribute-Value Pair)**
The encoding unit of RADIUS attributes. Each AVP consists of: 1-byte Type, 1-byte Length, and N-byte Value. For Vendor-Specific attributes (type 26), the Value contains a 4-byte Vendor-ID followed by nested sub-AVPs. Also called "attribute" generically.

**BNG (Broadband Network Gateway)**
A router that terminates PPPoE or IPoE subscriber sessions. The BNG is the NAS from the RADIUS server's perspective. It sends Access-Requests on behalf of subscribers and receives policy from the RADIUS server. Huawei's ME60 series is a common BNG in ISP deployments. radstorm simulates the subscriber-facing side of the BNG's RADIUS behaviour.

**Cascade failure**
A failure mode where an initial slowdown causes retransmits, which increase load on an already-stressed server, causing more slowdowns, more retransmits, and so on. Visible in radstorm results as `server_health.unresponsive_periods` followed by a spike in `retransmits.total`. The establishment curve shows `in_flight` rising after the activation peak rather than declining.

**CHAP (Challenge Handshake Authentication Protocol)**
An authentication method where the server never sees the plaintext password. The NAS sends a random challenge; the client responds with MD5(CHAP-Identifier | password | challenge). The RADIUS server independently computes the same hash using the stored password and compares. More secure than PAP but requires the RADIUS server to store reversible passwords (or use a pre-hashed scheme). See also PAP.

**CoA (Change of Authorization)**
A Dynamic Authorization Extension (RFC 5176). The RADIUS server sends a CoA-Request to the NAS to modify a live session (e.g., change rate limit, apply a new policy profile). The NAS responds with CoA-ACK (change applied) or CoA-NAK (change rejected). radstorm receives CoA-Requests on its CoA listener port (default 3799) and responds with ACK or NAK.

**Cold start**
In radstorm's scenario model, a cold start simulates a mass reconnect event: all subscribers in a population attempt to re-authenticate within a narrow time window, following a Gaussian distribution. This mirrors the real-world behaviour after a BNG or core link failure — CPE modems see the link restore and immediately start re-dialing, producing a surge of authentication requests.

**Disconnect**
A Dynamic Authorization Extension (RFC 5176). The RADIUS server sends a Disconnect-Request to the NAS to terminate a subscriber session immediately. The NAS responds with Disconnect-ACK or Disconnect-NAK. In radstorm, Disconnect-Requests are handled by the same listener as CoA-Requests.

**Drain**
The phase at the end of a radstorm run when no new subscribers are activated, but existing in-flight requests are allowed to complete. The drain period is configurable (`--drain-seconds`). After the drain timeout, any remaining in-flight subscribers are marked `auth_failed` and the run completes. The `still_in_flight_at_end` field in summary.json shows how many were still pending when the drain timed out.

**Ephemeral port**
A source port selected from the OS ephemeral port range (configured via `net.ipv4.ip_local_port_range` on Linux). radstorm binds UDP sockets on specific source ports within the `source.port_range` config to control which 4-tuples are available for RADIUS Identifier allocation. These are different from the OS ephemeral ports used by other applications.

**Establishment**
The state where a subscriber has completed both authentication (received Access-Accept) and accounting (received Accounting-Response for an Acct-Status-Type=Start). A subscriber in the `established` state has successfully traversed the full auth+acct flow. `subscribers.established` in summary.json counts how many reached this state.

**Framed-IP-Address**
RADIUS attribute 8. The IP address assigned to the subscriber's PPP session. In radstorm, each subscriber gets a mock Framed-IP-Address derived from its index in the subscriber pool. This address is included in Accounting-Start packets. The RADIUS server may use it for session lookup in CoA/Disconnect flows.

**Identifier (8-bit)**
A 1-byte field in the RADIUS packet header, values 0–255. Used to correlate replies with requests: the server copies the Identifier from the request into its reply. The Identifier must be unique per `(srcIP, srcPort, dstIP, dstPort)` 4-tuple while a request is outstanding. This is the fundamental capacity limit of the RADIUS protocol: 256 concurrent in-flight requests per 4-tuple. radstorm's ID allocator manages a bitmap of 256 IDs per tuple.

**In-flight**
A subscriber (or request) that has been sent but for which no reply has yet been received. The `in_flight` counter in the establishment curve tracks how many subscribers are in this state at each moment. High `in_flight` counts indicate the server is processing slowly relative to the activation rate.

**Message-Authenticator**
RADIUS attribute 80 (RFC 2869). An HMAC-MD5 over the entire packet keyed by the shared secret, computed with the Message-Authenticator value field zeroed during calculation. Required on CoA-Request and Disconnect-Request (RFC 5176). radstorm validates Message-Authenticator on all inbound packets that include it, and includes it in its CoA-ACK/NAK responses.

**NAS (Network Access Server)**
The device that performs access control on behalf of subscribers and communicates with the RADIUS server. In a PPPoE deployment, the BNG is the NAS. The NAS-IP-Address (attr 4) and NAS-Identifier (attr 32) identify the NAS to the RADIUS server. radstorm simulates a NAS for testing purposes.

**p50 / p95 / p99 / p99.9**
Percentile shorthand for latency distributions. p50 is the median — half of samples are below this value. p99 means 99% of samples are below this value (equivalently: 1 in 100 samples exceeds it). p99.9 (or p999) means 1 in 1000 samples exceeds it. At 1M subscribers, p999 represents 1000 real CPE sessions. radstorm reports min, p50, p95, p99, p999 (written as `p999` in JSON), and max.

**PAP (Password Authentication Protocol)**
An authentication method where the password is XOR-encrypted with MD5(SharedSecret | RequestAuthenticator) and sent as User-Password (attr 2). Simple but requires the RADIUS server to store the password in reversible form. Less secure than CHAP but widely supported. Most ISP PPPoE deployments use PAP for simplicity. See also CHAP.

**Parquet**
A columnar binary file format (Apache Parquet). radstorm writes event logs and subscriber outcome data as Parquet files for efficient post-run analysis. Parquet files can be queried with DuckDB, Apache Spark, pandas, or any tool that supports the format. The files are Snappy-compressed. See `events-shard-*.parquet` and `subscribers.parquet` in the run output.

**Pessimal**
In radstorm's scenario model, the pessimal scenario activates all subscribers simultaneously (or within a short `burst_window_ms`). This is the worst possible case from the RADIUS server's perspective — it receives the maximum possible concurrent load in the minimum possible time. Not realistic for production planning, but useful for identifying bottlenecks that a Gaussian ramp would not surface.

**Sharded collector**
radstorm's internal event collection system uses N independent in-memory buffers (one per CPU core), called shards. Subscribers are hashed to a shard. Each shard has its own Parquet writer that flushes independently. This design avoids a single bottleneck under high event rates (e.g., 1M Access-Requests in <1s). The result is multiple `events-shard-*.parquet` files, one per CPU core.

**Source IP alias**
An additional IP address bound to a network interface on the test host. Used to increase the number of available `(srcIP, srcPort)` pairs, which directly increases the number of concurrent in-flight RADIUS requests radstorm can support (each pair can hold 256 IDs). See `ip addr add` in docs/PRODUCTION-DEPLOYMENT.md §5.

**Tail**
The high-percentile end of a latency distribution. "Long tail" refers to a distribution where most values are low but a small fraction are very high. In RADIUS performance analysis, tail latency (p99.9 and above) matters because even a small fraction of slow authentications represents real customers experiencing failed logins. A candidate server with a shorter tail (lower p999 relative to p99) is generally preferable for a large subscriber population.

**Tuple (4-tuple)**
In radstorm's context: the combination `(srcIP, srcPort, dstIP, dstPort)` that identifies a UDP flow. The RADIUS Identifier namespace is scoped per tuple — two different tuples can use the same 8-bit Identifier simultaneously without conflict. Expanding the number of available tuples (via source IP aliases and port range) directly increases radstorm's maximum concurrent inflight capacity.

**VSA (Vendor-Specific Attribute)**
RADIUS attribute 26. Contains a 4-byte Vendor-ID followed by vendor-defined sub-attributes. Huawei's VSAs (vendor-id 2011) are used for BNG-specific policy attributes such as rate limiting (`Huawei-Input-Peak-Rate`) and session targeting (`Huawei-Connect-Id`). radstorm can send Huawei VSAs in Access-Requests (configured via `[nas.huawei]`) and parse them in inbound CoA-Requests.
